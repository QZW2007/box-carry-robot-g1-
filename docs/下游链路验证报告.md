## 4. 为什么 md5 不同：一个必须写清楚的发现

我逐层排除了所有可能，每一步都有证据：

| 假设 | 验证 | 结论 |
|---|---|---|
| 输入 world npz 不同 | 逐字段对比 | ❌ 全为 `0` 差异 |
| 命令行参数不同 | 逐字复制 `run_v29.ps1` | ❌ 完全相同 |
| 缺诊断开关（`--hand_diag --place_diag`） | 补上重跑 | ❌ 仍 `b6b7108f` |
| 路径敏感性 | 用 v29 的**原始相对路径** | ❌ 仍 `b6b7108f` |
| 非确定性（多线程） | 连跑两次 | ❌ 两次 md5 相同 ⇒ **确定性** |
| **渲染脚本在 v29 之后被改过** | **mtime 对比** | ✅ **就是这个** |

**证据**：

```
v29 渲染完成       : 2026-10-06 14:51:09
vis_robot_with_box.py 修改 : 2026-10-06 16:19:40   ← 晚 89 分钟
```

那 89 分钟后正是 **手部穿模修复** 那一批工作
（`hand_palm_audit.py` 15:13、`hand_roll_solve.py` 15:14、… `hand_clip_verify.py` 16:07、
渲染器 16:19）。

**独立的交叉证据**（来自日志，无需读代码）：

| 指标 | v29（交付） | 我的复现 |
|---|---|---|
| `right_wrist_roll_link` 穿模帧数 | **141**/354 | **144**/354 |

差 3 帧 —— 与 `box_pos` 差 70 帧（f145–f214，全在 carry 段）一致。
渲染器的手部处理改动会经由 **GRIP CLAMP**（箱心锚在手中点 + 低通漂移）
传递到 `box_pos`。

**漂移量**：中位 **22.9 mm**、p90 32.5 mm、max **34.9 mm**，全部在 carry 段内。
量级小、不影响观感，但它说明**当前的渲染器已经不是产出交付片的那个版本**。

## 5. 这件事的意义（要写进 `agent_taxonomy.md`）

1. **对 P1 的意义（好消息）**：下游链路**接线正确、可复现交付结论**。
   `align` 逐位一致，`render+qa` 复现出同样的 QA 判定与同样的失败帧区间。

2. **对交付物的意义（需要标注的事实）**：
   **交付的 v29 用当前代码无法逐字节重现**，因为渲染器在交付后被改过。
   这不代表交付片有问题（它的 QA 判定与重跑一致，失败项也仍是已知可接受项），
   但**任何人日后想"重跑一遍 v29"都会得到 `b6b7108f` 而不是 `63473c15`**。
   已交付的 mp4/npz（`79945c37` / `63473c15`）是**不可再生的快照**。

3. **对 Agent 的意义（一个新的失败模式）**：
   这是"**代码版本漂移**"型失败 —— 输入全对、参数全对，但**引擎变了**。
   通用做法是让每个阶段记录**脚本指纹**（hash + mtime），
   在产物元数据里带上，这样"为什么复现不出来"一眼可查。
   本次就是靠 mtime 才定位到的。**建议加进后续迭代**（当前未实现）。

## 8. 首次真跑 `--full` 暴露并修掉的两个缺陷（2026-10-07 补）

用你们那种方式跑了一次**完整 `--full`**（15:24 启动，`wall_secs = 462`），
链路四阶段全产出、`err.log` 为空、fit 一次通过（`fit_ok_ratio = 1.0`）。
但最终判定是 `qa_fail_review / ask=true`，**与我预测的 `qa_known_acceptable` 不符**。
查清后是**我代码里的两个真缺陷**，不是链路问题。

### 缺陷 1：`--full` 只传了"最小四件套"，复现不出交付片

| | 交付片 v29 | 修复前的 FULLRUN |
|---|---|---|
| `GRIP CLAMP` 漂移上限 | **450 mm** | **50 mm** ← 根因 |
| CARRY rot max | 12.277° | 6.221° |
| STOOL parked pos max | 7.4 mm | **15.7 mm** |
| QA 首个失败帧 | f159–164（TELEPORT×5） | **f280–281**（一次正常交接跳） |
| 最终判定 | `qa_known_acceptable` | `qa_fail_review` |

**原因**：`run_downstream()` 只自动传了 `box_size` / `quat_max_step_deg` /
`box_sym_snap` / `hand_roll_deg` 四个参数，而 v29 是靠
`run_v29.ps1` **逐字调参**的（30+ 个开关）。
**渲染器默认值 ≠ 交付参数** —— 所以"能跑通"与"复现交付片"是两件事。

**修法**：把 `run_v29.ps1` 的整套抽成 `run_agent.RENDER_TUNED`，
作为 `--full` 的**默认**渲染参数。想跑裸默认就传 `render_extra=[]`。
`verify_full_downstream.py` 也改为引用同一个常量，避免两处漂移。

### 缺陷 2：QA 的 slew cap 没跟随渲染的 cap（真实误报）

QA 脚本 `CARRY_ROT_MAX` 默认 **3.5**，而渲染可以用
`--quat_max_step_deg 20`（v29 就是）。两者不联动时，QA 会对
**故意放宽限速的渲染**报：

```
WARN: carry rot max 6.22 deg > 3.5 deg slew cap
```

而 SKILL 的验收里这**不是**问题（限速是为**真实转动**放宽的，见 SKILL：
"pass it as `--carry_rot_max <cap>`"）。`render_and_qa` 虽有
`carry_rot_max` 参数，但调用方从没传过，所以永远走默认 3.5。

**修法**：`render_and_qa` 在未显式给 `carry_rot_max` 时，
**自动从 `extra_args` 里读 `--quat_max_step_deg`**，并在返回里带
`carry_rot_max` 与 `carry_rot_max_src`（可追溯）。

### 修复后实测（同一次 `verify_full_downstream`，22 秒）

| 量 | 修复前 | 修复后 |
|---|---|---|
| QA 收到的 `carry_rot_max` | 未传（默认 3.5） | **20.0**（`from --quat_max_step_deg`） |
| 渲染参数个数 | 4 | **61** |
| CARRY rot max（QA 读出） | 6.221° | **12.277°** = 交付片 ✅ |
| QA 首个失败帧 | 280 | **159** ✅ |
| 最终判定 | `qa_fail_review / ask=true` | **`qa_known_acceptable / ask=false`** ✅ |
| `carry rot > 3.5` 误报 WARN | 有 | **消失** ✅ |

四条测试套件在修复后仍全绿（`parse_metrics` / `19/19` / `tools` / `A=PASS B=PASS`）。

> **教训（可迁移）**：把"能跑通"当成"复现了交付结果"是错的。
> 渲染器有 30+ 个开关，默认值不是交付值；只要有一处没带，
> 输出就变（本例 450→50 mm 的夹持漂移上限直接把失败点从 f159 挪到 f280）。
> 这类差异**不会报错**，只会静默地换一条片子。
